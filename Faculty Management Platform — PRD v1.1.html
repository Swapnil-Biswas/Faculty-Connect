Faculty Management, Productivity & Recognition Platform

Product Requirements Document (PRD) — v1.1

(v1.1: added system-level Admin role — see §3, §5.1, §6) Base concept: Intelligent Academic Data Synchronization Platform — "Enter Once – Use Everywhere" Status: Greenfield build (no existing code) · Stack confirmed: Next.js, React, TypeScript, Node.js, PostgreSQL, Prisma, Redis + BullMQ, Tailwind CSS Document status: Living document — new feature sets will be appended as new sections/versions as they're provided.

1. Vision & Problem Statement

Faculty in engineering departments re-enter the same academic data across ERP portals, spreadsheets, accreditation files, and departmental records. This wastes time and creates inconsistent records. The platform centralizes academic data entry once and propagates it everywhere it's needed — reports, accreditation (NBA/NAAC), analytics, and now, faculty management itself.

This PRD extends that core sync engine with a full Faculty Management, Productivity, Engagement, Notification, and Analytics layer, organized around a department hierarchy (HOD → Cluster Head → Faculty).

2. Goals

Goal Success Metric
Eliminate duplicate data entry Every fact (publication, task, leave, evaluation) is stored once, referenced everywhere
Give faculty visible recognition Daily leaderboard refresh, monthly Faculty-of-the-Month, no more than one notification per meaningful event
Give Cluster Heads real management tools Task assignment, leave approval, evaluation — all in one dashboard
Give HOD department-wide analytics Drill-down navigation: Department → Cluster → Faculty
Keep scoring fair and non-gameable Weighting formula is admin-configurable, not hardcoded; combines automatic + manual factors
Preserve auditability Every approval, evaluation, and score change is logged with actor + timestamp

4. System Architecture Overview

Next.js (App Router) — SSR dashboards, React Server Components for data-heavy views
   │
   ├─ API layer (Node.js, REST or tRPC) — auth, RBAC middleware, business logic
   │
   ├─ PostgreSQL (Prisma ORM) — single source of truth, one schema, no duplicate tables per feature
   │
   ├─ Redis + BullMQ — queues for: daily leaderboard recompute, notification dispatch,
   │      monthly Faculty-of-the-Month job, scheduled deadline/overdue checks, export generation
   │
   └─ Sync Engine (core, pre-existing concept) — central write path; every module writes through
          it so "enter once" facts (publications, task completions, leave outcomes) fan out to
          Faculty Dashboard, Cluster Dashboard, HOD Dashboard, Leaderboard, Analytics, Exports
          without being re-entered.

Key architectural decision: the Sync Engine is not a separate microservice for v1 — it's a service-layer module (syncEngine.ts) that every domain service (tasks, leave, recognition, publications) calls after a write, which then invalidates/updates derived views (leaderboard cache, dashboard aggregates, notification triggers). This keeps the "modular monolith" simple to build with a 2-person team while preserving the single-write-fans-out principle. Can be split into real services later if scale demands it.

5. Functional Modules

5.1 Faculty Hierarchy & RBAC

  • Entities: Department, Cluster, User (role: Admin/HOD/ClusterHead/Faculty), ClusterMembership.
  • Admin is a system-level role, not tied to any department — provisioned outside the normal app flow (e.g., seeded directly in the DB / env-based bootstrap on first deploy), never self-registered.
  • HOD is department-scoped (singleton per department in v1) and is created/assigned only by Admin — HODs cannot self-promote or be created by Cluster Heads. Cluster Head belongs to one cluster; Faculty belongs to exactly one cluster.
  • Normal provisioning chain: Admin creates HOD → HOD provisions Cluster Heads → Cluster Heads add Faculty. Admin can also short-circuit any step directly (create a Cluster Head or Faculty without going through HOD) — this is intentional "full control," used for fixes/edge cases, not the default path.
  • Role changes (promote/demote/reassign) are themselves audit-logged events, not silent field updates.

5.2 CL / Leave Application

  • States: PENDING → APPROVED | REJECTED, plus CANCELLED (faculty-initiated, only while pending).
  • LeaveApplication: dates, reason, remarks (Cluster Head), decidedBy, decidedAt.
  • Every state transition fires a notification event and an audit entry.

5.3 Task Management

  • Task: title, description, assignedTo, assignedBy, priority, deadline, status (OPEN/IN_PROGRESS/COMPLETED/OVERDUE), completedAt, remarks, qualityRating.
  • Derived (computed, not stored redundantly): completedBeforeDeadline, daysToComplete — calculated from deadline/completedAt at read time or cached on completion.
  • Scheduled job flags tasks OVERDUE daily and triggers a notification.

5.4 Recognition Engine (Stars/Points)

  • Automatic factors (computed by system): on-time completion, early completion, completion rate, deadline adherence, consistency streak.
  • Manual factors (Cluster Head/HOD input): Quality (1–5), Contribution (1–5), Initiative (1–5), Overall (1–5), free-text remarks.
  • ScoringConfig table: admin-editable weight per factor (e.g., onTimeWeight: 0.3, qualityRatingWeight: 0.25, …), versioned so historical scores remain explainable even if weights change later.
  • PointsLedger: append-only log of every point-earning event (source, amount, reason, timestamp) — the faculty's total is a sum, never a mutable field, so "how did I earn my stars" is always answerable.

5.5 Leaderboard

  • Recomputed nightly via BullMQ job from PointsLedger + task/eval data; snapshot stored in LeaderboardSnapshot (date, faculty, rank, points) for weekly/monthly/semester/year views without recomputation.
  • Notification only on meaningful rank changes (configurable threshold, e.g., entering/exiting top 5) — not on every micro-shift.

5.6 Faculty of the Month

  • Scheduled job on month rollover: scores against ScoringConfig-weighted criteria over the prior month's window, picks winner, writes to FacultyOfTheMonth (month, year, facultyId, snapshotStats) — append-only, never overwritten, so history is browsable.

5.7 Encouragement / Gamification Layer

  • Badge, Achievement, Milestone tables — rule-evaluated (e.g., "10 tasks completed early" → badge) by the same nightly job that recomputes the leaderboard, to avoid real-time overhead.
  • Framing note for UI copy: progress and recognition language, not surveillance language (per the source spec) — this is a UX/content guideline to carry into design, not a schema concern.

5.8 Notification System

  • Event-driven: domain services emit events (task.assigned, leave.approved, stars.awarded, leaderboard.refreshed, …) → a notification service consumes them → writes Notification row + optionally pushes via existing in-app channel.
  • NotificationRule table lets HOD configure which events actually notify (avoids spam on trivial rank shifts).
  • In-app requirements: bell icon, unread count, panel, read/unread state, timestamp, deep-link to the relevant record.

5.9 Dashboards

  • Faculty: tasks, deadlines, leave status, stars, badges, rank, recent notifications, monthly progress.
  • Cluster Head: cluster roster, task/leave queues, evaluations, cluster leaderboard, export.
  • HOD: all clusters, department analytics, Faculty of the Month, drill-down navigation (Dept → Cluster → Faculty).
  • Built as Next.js Server Components pulling pre-aggregated data (not raw joins per request) for performance.

5.10 CSV/Excel Export

  • Single export service, parameterized by scope (cluster | department | selectedFaculty | dateRange), enforces the RBAC matrix in §3 server-side before query execution — never trust a client-supplied scope.
  • Generates from live DB query at request time (BullMQ job for large exports to avoid blocking the request).

5.11 Research & Achievement Data

  • Publication, StudentAchievement entities feed both the original accreditation/reporting flow and the recognition engine — one entry point, consumed by both (this is the clearest "enter once" case in the new scope).

5.12 Audit & History

  • AuditLog: actorId, action, entityType, entityId, beforeState/afterState (jsonb), timestamp. Written by a single audit-logging middleware/service wrapper around all mutating operations — not scattered console.log-style calls — so coverage is consistent.

6. Non-Functional Requirements

  • RBAC enforced server-side on every endpoint, not just hidden in UI.
  • Idempotent scheduled jobs (BullMQ) — safe to re-run if a nightly job fails partway.
  • Explainability: every score/rank must be traceable to ledger entries and the scoring config version active at the time.
  • No duplicate entry: any new field added later must ask "does this already exist somewhere?" before creating a new input surface.
  • Admin power has no audit exemption: every Admin action — role changes, record edits, deletes, impersonation, config changes — writes to AuditLog with before/after state, exactly like every other role. There is no "untracked override" path, by design: it's what keeps §6's explainability guarantee true even at the top of the hierarchy.
  • Soft deletes only: Admin "delete" operations set a deletedAt timestamp rather than removing rows. Hard deletion (if ever needed) is a separate, rarer, explicitly-logged operation — not the default "remove" action.
  • Impersonation is fully logged: session start/end, actor, target user, and a flag on any action taken while impersonating, so it's never ambiguous who actually did what.
